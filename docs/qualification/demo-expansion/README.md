## Workload and architecture

All five 4B cases use identical six prompts and three planned arrival groups containing 1, 2 and 3 requests, at 0, 20,000 and 20,025 ms. Arrival groups are submission groups; actual model iterations have independently recorded membership. Each assessment requires the first request to finish before the reuse group, the third group to arrive while the second is active, multi-request iterations and overlapping prefill/decode. Configuration uses context 2,048, maximum three concurrent sequences, aggregate token budget 64, long-prefill cap 64, prefix caching, chunked prefill, a fixed 512 MiB KV budget and a 64-step eager diagnostic window.

The 4B repository and tokenizer revision is `cdbee75f17c01a7cc42f958dc650907174af0554`. FP8 weight storage is observed as CUDA E4M3FN while compute remains BF16; quantized loaded weight storage is 4,478,730,368 bytes versus 8,112,045,632 BF16 bytes. The FP8 KV case uses actual E4M3 storage. The same configured 512 MiB budget increases physical block capacity from 227 BF16 blocks (226 usable) to 455 FP8 blocks (454 usable), with one reserved null block in each; it does not imply halving the configured pool allocation. Actual allocated storage differs slightly because whole blocks are allocated.

The FP8 captures retain substantial pre-owner-exit process usage: 5,469,372,416 bytes for FP8 weights and 8,879,341,568 bytes for FP8 KV. ## Retained failures and unsupported configurations

The first BF16 attempt exposed a UUID namespace mismatch and an insufficient raw trace bound. The second exposed profiling finalization beyond the ordinary cleanup deadline. Both are retained. A valid earlier BF16 capture against an older source remains historical evidence; a fresh final-source capture replaces it in the primary demo. The first hybrid attempt exceeded the native trace bound and used an unsuitable short prefix; the second exceeded the browser attachment bound. Their failures motivated bounded lossless encoding, followed by the final successful capture. The authored initial LoRA qualification plans had an incorrectly placed adapter list and were rejected before API/GPU execution; corrected plans then passed. No production UI serializer defect was found there.

The supplied one-H100 PyPI runtime has no qualified Flash-Next or FP4 recording. The Flash-Next recipe uses a dedicated runtime and documents a much larger checkpoint/multi-H100 configuration. NVFP4/MXFP4 likewise have no qualified checkpoint/capture path here. Selectors show Unsupported rather than assigning another model's artifact to these options. Other compatible but unrecorded combinations require a fresh capture.
